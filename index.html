Drone Dispatch Service

Moving medicine by drone, without breaking the rules

Good morning everyone. My name is Kolade, I’m a backend engineer, and thank you for having me. Today I’ll walk you through the drone dispatch service I built. I’ll show you what it does, the parts that were actually hard, how I handled each one, and then a short live demo. After that, I’m open to any question. So feel free to pick at anything.

The problem

Lagos traffic vs a drone

In heavy traffic, a short trip can take hours. A drone just flies over it.

What I built

The backend for a control room that manages up to 10 medicine drones. Talking to the drones themselves was out of scope.

So let me set the scene. If you’ve ever been stuck in Lagos traffic, you know a trip that should take twenty minutes can take you hours. Now imagine you’re trying to get medicine to someone. A drone doesn’t care about any of that. It just flies over. So the task was to build the backend for the control room. The people in that room register drones, load them with medicine, check their battery, and see which ones are ready to go. Actually talking to the drone over radio was out of scope. My job was the backend, and making sure the rules are never broken.

These are the six things the service had to do. You can register a drone, see which drones are ready to be loaded, load medicine onto a drone, see what’s on board, check a drone’s battery, and there’s a background job that keeps a history of every drone’s battery. I added one extra: retiring a drone. In real life, you don’t just delete a drone that has carried medicine. It’s like a closed bank account. The bank doesn’t delete it, the history stays. So instead of deleting, you retire it.

Choices I made where it was open

Weight like money

You send grams. I store whole milligrams. Same idea as keeping money in kobo.

The edges are allowed

Exactly 25% battery can load. You can fill a drone to exactly its limit.

Every trip is a delivery

Back to IDLE closes it. Nothing is deleted, it stays as history.

Battery comes from the drone

A PATCH endpoint stands in for the drone sending its battery level.

Some parts were open, so I made a decision and wrote each one down in the README. Four of them matter most. First, I treat weight like money. You send me grams, but I store whole milligrams, the same way we keep money in kobo and not in naira. I’ll show you why in a few slides. Second, the edges are allowed. A drone at exactly 25% can still load, and you can fill a drone to exactly its limit. Third, every trip is a delivery. When the drone comes back to IDLE, the delivery is closed, but I keep it as history. And fourth, since we can’t talk to real drones, there’s an endpoint that stands in for the drone reporting its own battery.

Safe to change

Rules are checked when you act, so old drones don’t break.

One thing I made sure of: the business can change its rules without a developer touching the code. Every limit is a setting. The fleet size, the max weight, the battery minimum, how often the battery job runs, the rate limit, and so on. So let’s say we buy bigger drones tomorrow. We change the max weight to 1000 grams, restart the app, and that’s it. No code change, no migration. Every setting is also checked when the app starts. If someone mistakenly sets the battery minimum to 150%, the app won’t start, and it tells you exactly what’s wrong. I’d rather it fail at startup than in production. And changing a limit doesn’t break old data, because the rules are checked at the moment you act. If the minimum goes from 25 to 30, a drone at 28% just can’t take more load. Nothing else breaks. If one day they need to change these without a restart, the next step would be a settings table. I didn’t build that because it wasn’t needed yet.

What I used, and why

NestJS + TypeScript. Modules, dependency injection, guards and validation built in. Every feature has the same shape.

PostgreSQL 16. Real transactions, row locks and constraints.

Prisma 7. Typed queries and migrations. Raw SQL only for locks.

Docker + GitHub Actions. One command to run it. Every PR checked.

This is how it’s put together. It’s one app, split into clear modules: drones, medications, battery and health. When a request comes in, it first goes through the rate limit, then the API key check. The controllers only check the input. All the actual rules live in the services, and they run inside one database transaction. On the side, there’s a battery job that runs every minute. For the stack, I used NestJS with TypeScript, because it gives me structure out of the box. Modules, dependency injection, guards, validation, all built in. So every feature has the same shape, and anyone joining the team knows exactly where things go. Postgres, because I needed real transactions and row locks, and you’ll see why in a minute. And Prisma for typed queries and migrations. I only wrote raw SQL where I needed a lock.

A drone’s life

IDLE→ LOADING→ LOADED→ DELIVERING→ DELIVERED→ RETURNING

Back to IDLE

From RETURNING, or from LOADING to cancel. The delivery closes and the drone is emptied. The history stays.

Battery rule

Moving to LOADING or LOADED needs at least 25% battery.

Nothing on board

A drone can’t be LOADED while it’s empty.

The allowed moves are in one table in the code. Anything else gets 409 INVALID_STATE_TRANSITION, and the error lists the moves you can make.

Every drone goes round this cycle. It starts IDLE. While we put medicine on it, it’s LOADING. When it’s ready, it’s LOADED. Then DELIVERING, DELIVERED, and RETURNING on the way back. When it gets back to IDLE, the delivery is closed and the drone is empty again, but the delivery stays as history. I kept all the allowed moves in one table in the code, not if statements spread everywhere. So it’s easy to read and easy to test. There’s a test for every move that’s allowed, and every move that isn’t.

The real work

Making it work was easy. Making it safe when things happen at the same time was the real work.

For every feature, I asked: what breaks?

Now, honestly, getting it to work was the easy part. Check the weight, save it, done. The real work was everything around that. What happens when two requests come in at the same time? What happens when a client retries? What happens when the numbers have decimals? So for every feature, I kept asking myself one question: what breaks? The next few slides are my answers.

Challenge 1

Two loads on one drone, at the same time

Without a lock

  1. A reads 300g. B reads 300g.
  2. Both check 300 + 150 = 450. Both pass.
  3. Both save. The 500g drone now has 600g.

With a row lock

  1. A locks the drone’s row. B waits.
  2. A saves 450g.
  3. B reads 450g. 450 + 150 = 600. Rejected.
Backup rule in the database: loaded weight can never be more than the limit. Even a bug can’t save an overweight drone.
This is the one I care about the most. Picture two people loading the same drone at the exact same moment. The drone already has 300 grams, and each of them wants to add 150. Without a lock, they both read 300. They both check that 450 is under 500. And they both save. Now a 500 gram drone is carrying 600 grams. It’s the same thing as two POS terminals debiting one account at the same time. Somebody will call customer care, and it won’t be the engineer. So what I did is: inside the transaction, I lock that drone’s row first. The second request has to wait. When it finally gets in, it sees 450, adds 150, gets 600, and it’s rejected. Other drones don’t wait at all, only that one drone. And as a backup, the database itself has a rule: the loaded weight can never be more than the limit. So even if there’s a bug in my code someday, the database still won’t save an overweight drone. (If asked why not a conditional update like a wallet debit: it’s faster, but it can’t tell you which rule failed, and I check three things here: state, battery and weight.)

I picked numbers where the right answer is obvious. Take the lock away and this test fails.

Now, anybody can say “I handled race conditions”. I wanted to prove it. So I wrote a test with numbers where the right answer is obvious. One drone with a 500 gram limit. Every request adds one item of 120 grams. If you do the maths, only 4 can ever fit. That’s 480 grams. A fifth one would make it 600. The test sends 20 of those requests at the exact same time. If the lock works, exactly 4 get in, 16 get rejected, and the drone ends up at 480 grams. The test also checks that the weight saved on the drone matches the items in the database. And if I remove the lock, more than 4 get in and the test fails. That’s how I know the lock is really doing the work.

Challenge 2

The retry that loads twice

The client times out. It doesn’t know if the load went through, so it sends it again with the same Idempotency-Key.

Same key, same body

You get the first answer back. Nothing loads twice.

Same key, new body

Rejected with 409. One key, one request.

Both at once

Postgres makes the second one wait, then gives it the first answer.

The key is saved in the same transaction as the load. That’s why I didn’t use Redis. The key and the load can’t disagree.

The second problem is retries. In payments, we call this the double debit problem. The client sends a load, the network drops, and now it doesn’t know if the load went through. So it sends it again. If we just run it again, the drone gets loaded twice. So the load endpoint accepts an Idempotency-Key. It’s just a unique ID the client sends with the request. If the same key comes in with the same request, I send back the first answer, and nothing is loaded again. If the same key comes with a different request, that’s a 409, because one key means one request. And if two requests with the same key arrive at the exact same time, Postgres makes the second one wait, and then it gets the first answer. I didn’t need to write any extra locking for that. I kept the key in Postgres, in the same transaction as the load, so the key and the load can never disagree. That’s also why I didn’t need Redis. Only the load has a key, because the other writes are already safe to repeat. Registering the same drone twice is blocked by the serial number, and setting the battery to 40 twice gives the same result.

Challenge 3

Decimals don’t add up

0.1 + 0.2 = 0.30000000000000004
1.005 * 1000 = 1004.9999999999999

So I store whole milligrams, and only use grams at the edge of the API.

Grams come in. I convert once: times 1,000, rounded to a whole number. Anything finer than 1mg is rejected. Every check after that is whole numbers.

Third problem: decimals. Medicine weights have decimals, like 20.5 grams. And in JavaScript, 0.1 plus 0.2 doesn’t give you 0.3. It gives you 0.30000000000000004. The second line surprises a lot of people: 1.005 times 1000 should be 1005, but you get 1004.9999. If I stored weights like that, my weight check would be wrong right at the limit, which is exactly where it matters. So I did what we do with money: kobo, not naira. Here’s how it works. When a weight comes in, I convert it to milligrams once. I multiply by 1000, and I round to the nearest whole number. So that 1004.9999 becomes 1005, which is what it should be. But before I round, I check that the person didn’t send more than three decimal places. If someone sends 12.3456 grams, that’s smaller than one milligram, so I reject it instead of quietly rounding it. From there, every sum and every check is on whole numbers, so it’s always exact. I only divide by 1000 again when I send the answer back in grams. So 3 times 20.5 plus 22.5 comes out as exactly 84 grams.

Challenge 4

When there’s no row to lock

The fleet of 10

Two sign-ups when we have 9 drones. Both count 9, both get in, now we have 11. There’s no “fleet” row to lock, so I lock a name instead. Postgres calls it an advisory lock.

The battery job

One insert writes 1,000 drones at a time. If the last run is still going, it skips. With 3 copies of the app, the same kind of lock lets only one of them write.

Battery under 25%? Like a danfo driver on the fuel light. He won’t take you to Ikorodu.

Sometimes there’s no row to lock. The fleet can only have 10 drones. Imagine we have 9, and two people register a drone at the same time. Both count 9, both say there’s space, and now we have 11. There’s no “fleet” row I can lock, so I lock a name instead. Postgres calls that an advisory lock. Prisma itself uses the same idea so that two migrations don’t run at once. The battery job is similar. Every minute, it writes every drone’s battery level to a history table. It does it in batches of 1000 with one insert each, not one query per drone. If a run is slow, the next one just skips. And in production we might run three copies of this app. Without a lock, all three would write the history, so you’d get three times the rows. With the lock, only one of them writes. And about the 25% rule: it’s like a danfo driver with the fuel light on. He won’t agree to take you to Ikorodu.

What I chose not to build

No Redis

Nothing needs caching. Postgres already holds the locks and the retry keys.

No queue

Every request ends in one short transaction. A queue makes sense when real drones send data.

No microservices

One small domain, one database. The modules can split later if we need it.

Only 2 rules live in the database

Weight never over the limit, and one open delivery per drone. Things that can change, like 500g or 25%, stay in config.

Knowing what not to build is also part of the job. I didn’t add Redis, because nothing here needs caching, and Postgres already holds the locks and the retry keys. I didn’t add a queue, because every request finishes in one short transaction. When real drones start sending us data, that’s when a queue makes sense. And no microservices for one small domain. It’s split into clean modules, so it can be split later if we ever need to. In the database itself, I only put two rules: the weight can never go over the limit, and a drone can only have one open delivery. Things that can change, like the 500 grams or the 25%, stay in config. If I put 500 inside the database and the business wanted 1000 next year, I’d need a migration just to change a number.

Going to production, and what’s next

Before production

  • Secrets from a secret manager
  • Migrations once per release, safe for the old version
  • A shared store for the rate limit across instances
  • Logs sent to Grafana Loki
  • Clean up old battery logs on a schedule

Next steps

  • Drone data coming in through a queue
  • Cursor pagination for big tables
  • Image upload with pre-signed S3 links
  • User accounts and roles
  • One API key per client
If this were going to production tomorrow, here’s what I’d do first. The secrets would come from a secret manager, not from env files. Migrations would run once per release, and I’d keep each one safe for the old version while the new one rolls out. With more than one copy of the app, the locks already work across all of them. But the rate limit counter lives in memory, so it would need a shared store like Redis. That’s when Redis actually earns its place. The logs are already JSON with a request ID, so they’re ready for Grafana Loki. And the battery history grows every minute, so it needs a cleanup schedule. After that, the next features would be: real drone data coming in through a queue, cursor pagination for very big tables, image upload, user accounts and roles, and one API key per client instead of one shared key.
